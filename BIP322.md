# Bitcoin message proofs (BIP-322 simple)

The maintained Bare and Node binding overlay adds address-based Bitcoin message proofs without changing the upstream RLN repository, its Lightning message signer, or the remote signer protocol. It does not enable Lightning in an application.

```js
const address = node.getMessageSigningAddress()
const signature = node.signMessageBip322(' exact message\n', address)
const valid = verifyMessageBip322(' exact message\n', address, signature, 'regtest')
```

`getMessageSigningAddress()` and `signMessageBip322()` require an unlocked node with its matching native external signer attached. The canonical signing address is the first vanilla Taproot address at `m/86'/coin_type'/0'/0/0` (coin type 0 on mainnet, 1 on other networks). It is stable, can differ from the current rotating receive address, and does not allocate an address or update wallet state. This initial version deliberately signs only that address. Supplying another address, including another address from the same wallet, fails.

The private key derives inside the native signer from the same 32-byte seed and account derivation as the pinned VLS adapter. Its account xpub is checked against the actual native signer bootstrap before admission. Only the first address scalar is retained, under the signer's existing read/write shutdown gate. Shutdown waits for active signing and destroys that scalar with the backend state, revoking all retained signer clones. Before every proof/address request, the attachment must match both the live unlocked node identity and every persisted wallet bootstrap field. This rejects replacing the attached signer after a wallet is already unlocked. Existing native node locking and terminal shutdown checks apply. No private key is returned to JavaScript or written to a new file.

Messages are exact valid UTF-8: no trimming, normalization, prefix length, or terminating NUL is added. Empty messages and embedded NUL are supported. The maximum is 4,096 UTF-8 bytes; malformed UTF-16 input is rejected before marshalling. New methods use escaped JSON across the C boundary so NUL cannot truncate a message. No caller-supplied transaction, PSBT, digest, derivation path or sighash flag is accepted. The only transactions constructed are BIP-322's unspendable virtual transactions; there is no network request or broadcast path.

The signer emits a `smp`-prefixed simple proof, as required by the finalized BIP-322 v2.0.0 format. Taproot key-path signatures use `SIGHASH_DEFAULT` and fresh OS auxiliary randomness. Legacy `signMessage()` and `verifyMessage()` retain their Lightning node-identity semantics; they are not address proofs.

The module-level `verifyMessageBip322(message, address, signature, network)` needs no node, wallet, signer, unlocked session or network connection. The node method `verifyMessageBip322(message, address, signature)` uses the configured node network and can verify while locked. Verification accepts finalized `smp` and historical prefixless simple encodings for:

- P2TR key-path: one 64-byte DEFAULT or 65-byte ALL signature; no annex or script path.
- P2WPKH: compressed public key, exact key hash, strict DER, low-S and ALL only.

The verifier rejects malformed/noncanonical base64, nonminimal or oversized witness fields, trailing bytes, extra items and other sighash types. Unsupported address/script forms, full and proof-of-funds formats are not supported. Unsupported address types are rejected with an error or `false`; the API never reports them as successfully verified. A cryptographic failure returns `false`. Messages, addresses, signatures and network parameters have explicit native and JS bounds. A proof does not prove current funds, establish the signer's real-world identity, or grant a transaction authorization. Applications must present the exact address/message and apply their own fresh authorization and request-domain policy.

The runtime capability is `bip322-simple-v1`. Consumers must check both this compiled capability and the corresponding method exports; old native binaries must fail admission rather than silently fallback to Lightning signing.

## Verification

Run `npm run test:bip322:crypto` with Rust 1.94.0. The harness extracts the exact crypto module from the pinned native overlay, then checks its virtual transaction hashes, supported official positive/negative vectors, exact UTF-8/limits/ownership, malformed witness boundaries, and independent scure/noble P2TR and P2WPKH vectors. Test keys are published public fixtures and must never hold funds. `npm run test:installer`, `npm run check:types` and the host runtime tests cover facade and artifact/lifecycle admission. Native target builds require the normal documented private upstream dependencies; this feature introduces no new native dependency or floating source pin.

Independent supplemental vectors were generated using public official test WIFs with @scure/btc-signer and @noble/curves; they include mathematically valid forbidden-sighash and high-S cases.
